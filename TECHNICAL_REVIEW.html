CRM Contacts: Technical Review Answers

Concise answers about the implemented architecture, behavior, tests, and current trade-offs.

1. Code structure

The directory UI is in ContactsWorkspace; reusable directory reads and async state are in useContactDirectory. Form behavior is isolated in ContactDialog. Route Handlers validate HTTP input, services compose reads, and repositories own database operations.

2. API and server state

Loading, empty, success, and error states are explicit. Superseded reads are cancelled with AbortController, and the last successful results remain visible during background loading. A custom hook is used instead of TanStack Query because the app has one main directory view; the trade-off is no shared cache, retries, or background refetching.

3. Search, filters, and navigation

Search is debounced by 300 ms. Search, company/tag filters, sorting, and pagination are URL-backed. Filter and sort changes reset the page. Directory reads are paginated on the server.

4. Forms and concurrent updates

Formik manages form state and Zod validates fields on both client and server. Unsaved edits are guarded on close and page unload. Contact and tag mutations compare the supplied version with the stored version and increment it on success. A stale write returns HTTP 409 with the latest record; the dialog compares draft and server values and supports accepting latest values or merging only the user's changed fields/tags before retrying.

5. Accessibility and responsive UX

Fields are labelled and connect validation messages with ARIA attributes. The dialog sets and restores focus, traps keyboard focus, and supports Escape. Async feedback uses live status/alert regions. The desktop table becomes contact cards on narrow screens while pagination remains visible.

6. React and code quality

Hooks remain at component top level; fetch effects clean up by aborting requests. Form and query state are controlled, and the directory read logic is not embedded in layout rendering. The implementation avoids global state and additional libraries where the app does not need them.

7. Meaningful tests

Vitest covers API validation, duplicate normalized email/phone values, successful and stale contact updates, stale tag writes, and field/tag merge behavior. Lint and TypeScript checks are also run. Manual browser checks complement automated tests for focus and responsive layout.

8. Performance and maintainability

Server pagination, relevant database indexes, debounce, and request cancellation keep work bounded. Virtualization and prefetching are unnecessary for the current page size. Known gaps include no authentication/authorization, offline queue, real-time updates, tag CRUD, or contact deletion. Bulk tag updates are sequential and can partially succeed.
